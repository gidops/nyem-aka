# Nyem Aka: Deployment

How to put the system online, in the order that works, and how to check each step.

```
Browser ──HTTPS──▶ Vercel (Next.js web app)
                     │  /api/*  is forwarded server-side
                     ▼
                   Render (NestJS API) ──▶ Neon (PostgreSQL)
                     │
                     └──▶ Cloudinary (fault images)
```

The browser only ever talks to the Vercel address. That is why the sign-in cookies work without any cross-site configuration.

**Order: GitHub → Neon → Cloudinary → Render → Vercel.** Each step needs something from the one before it: Render needs the database address and image credentials; Vercel needs the API's address.

All five services have a free tier that is enough for this project.

## What is already prepared

| File | Purpose |
| --- | --- |
| `render.yaml` | Describes the API service: build command, start command, health check, every environment variable |
| `apps/api/.env.example`, `apps/web/.env.example` | Every setting, with an explanation |
| `.github/workflows/ci.yml` | Tests run on every push once the code is on GitHub |

The production build and start commands have been run locally in a clean copy of the repository with production settings, so the commands themselves are known to work.

## 1. GitHub

Render and Vercel both deploy from a GitHub repository, and CI runs there.

1. Create a repository and push `main`.
2. Open the **Actions** tab and wait for the CI run. All three jobs (API, web, browser tests) should go green. This is the first time CI runs, so treat a failure as information: read the failing step's log.

## 2. Neon (database)

1. Sign up at <https://neon.tech> and create a project. Choose PostgreSQL 16 and the region closest to your Render region (the blueprint uses Frankfurt).
2. On the project dashboard, open **Connect**. Copy two connection strings:

   | Setting name | Which string | How to recognise it |
   | --- | --- | --- |
   | `DATABASE_URL` | **Pooled** connection | The host contains `-pooler` |
   | `DIRECT_URL` | **Direct** connection | Switch "Connection pooling" off; no `-pooler` in the host |

   Both should end with `?sslmode=require`.

**Why two.** The running API opens many short connections, which the pooler handles efficiently. Migrations need one long, direct connection, which the pooler does not allow.

You do not need to create tables by hand. The API applies the migrations itself each time it starts.

## 3. Cloudinary (images)

1. Sign up at <https://cloudinary.com>.
2. From the dashboard, copy **Cloud name**, **API key** and **API secret**.

3. Check them before deploying. Add the three values to `apps/api/.env` (never to a committed file), then run:

   ```bash
   npm run check:cloudinary -w api
   ```

   It uploads a tiny test image through the API's own storage code, fetches it back and deletes it. While those values are in `.env`, your local app also stores uploads on Cloudinary; remove them again to go back to local-disk storage.

**Why.** Render's disk is erased on every deploy, so uploaded images must live elsewhere. The API refuses to start in production without these three values, rather than silently losing images later.

## 4. Render (API)

1. Sign up at <https://render.com> with your GitHub account.
2. **New → Blueprint**, choose the repository. Render reads `render.yaml`.
3. It asks for the values marked as secrets:

   | Setting | Value |
   | --- | --- |
   | `DATABASE_URL` | Neon pooled string |
   | `DIRECT_URL` | Neon direct string |
   | `SEED_ADMIN_EMAIL` | The email the first administrator will sign in with |
   | `SEED_ADMIN_PASSWORD` | A strong password you choose (12+ characters). Store it in a password manager |
   | `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` | From Cloudinary |

   The two JWT secrets are generated by Render. Everything else has a value in the blueprint.
4. Apply. The first build takes a few minutes.

**What the start command does**, every time the service starts: applies any new migrations, runs the seed (roles, categories, the first admin; safe to repeat, and it never resets a password), then starts the server.

**Check.**

- `https://<your-api>.onrender.com/health` returns `{"status":"ok","database":"connected",…}`.
- `https://<your-api>.onrender.com/docs` shows the Swagger page.
- The deploy log contains `Seeded 3 roles, 7 categories, admin …`.

## 5. Vercel (web)

1. Sign up at <https://vercel.com> with your GitHub account.
2. **Add New → Project**, import the repository.
3. Set **Root Directory** to `apps/web`. Leave the framework as Next.js and the build settings on their defaults.
4. Add one environment variable:

   | Setting | Value |
   | --- | --- |
   | `API_URL` | `https://<your-api>.onrender.com` (no trailing slash) |

5. Deploy.

**Why `API_URL` must be set before building.** The `/api` forwarding rule is fixed when the app is built. If you change `API_URL` later, redeploy.

## 6. Smoke test in production

Do these on the Vercel address, on a laptop and then on a phone.

1. The landing page loads.
2. Sign in as the administrator you set in Render. Create a maintenance officer under **Users**.
3. In a private window, register a new account. Report a fault **with a photo**.
4. As the admin, assign it to the officer.
5. As the officer, start the work, add a photo, mark it completed.
6. As the requester, confirm the status, both photos and the full timeline.
7. As the admin, export the CSV and open **Audit trail**.

**Check the cookies.** In DevTools → Application → Cookies, `access_token` and `refresh_token` belong to the Vercel domain and are marked `HttpOnly` and `Secure`.

**Check images survive a deploy.** In Render, trigger **Manual Deploy**. Afterwards the photos from step 3 still display. (They are on Cloudinary; this confirms it.)

**Check the client address.** This matters for the login rate limit. Open **Audit trail** as admin and look at the *IP address* column for sign-ins made from two different networks (for example home Wi-Fi and mobile data).

| What you see | Meaning | Action |
| --- | --- | --- |
| Two different addresses, matching each network | Correct | None |
| The same address for everyone | The API is seeing a proxy, not the visitor, so all users share one login rate limit | Raise `TRUST_PROXY_HOPS` by 1 in Render and redeploy |
| An address the visitor could have typed themselves | Too many hops are trusted | Lower `TRUST_PROXY_HOPS` by 1 |

The blueprint starts at 2 (Vercel, then Render's own proxy), which was verified locally with a simulated two-proxy request but not against the real services.

## 7. After it works

- Put the live addresses in `README.md` and in the report.
- Take the report's deployment screenshots: the Render service page, the Vercel deployment page, the Neon dashboard.
- Run `npm run demo -w api` **only against your local database**, never production. For demo content online, create it by hand through the app.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Render deploy fails with "CLOUDINARY_… are required in production" | A Cloudinary value is missing | Add it under Environment and redeploy |
| Render deploy fails during `prisma migrate deploy` | `DIRECT_URL` is wrong, or is the pooled string | Use the direct string (no `-pooler`) |
| `/health` returns 503 | The API cannot reach Neon | Check `DATABASE_URL`, including `?sslmode=require` |
| First request after a quiet period takes up to a minute, or fails once | Free services sleep when idle (Render after 15 minutes, Neon after 5) | Wait and retry. Open the `/health` address a minute before a demonstration |
| Sign-in works on Render's `/docs` but not on the Vercel site | `API_URL` was missing or wrong when Vercel built | Set it and redeploy |
| Every `/api/...` call returns 404 on Vercel | Same as above | Same |
| A large photo fails to upload online but works locally | The hosting proxy limits request size | Try a smaller image; if confirmed, lower `MAX_ATTACHMENT_BYTES` in `attachments.service.ts` and the matching limit in `file-dropzone.tsx` |
| Signed out again after a few minutes | `JWT_REFRESH_SECRET` changed between deploys | Do not regenerate the JWT secrets; everyone must sign in again if you do |

## Known limits of the free tier

- **Cold starts.** Expect a slow first request after inactivity. State this in the report.
- **Not yet verified against the real services:** the Cloudinary upload and delete code, the proxy hop count, and the size limit for uploads passing through Vercel. Section 6 checks each one.
- **One region, one instance, no backups configured.** Fine for coursework; a real deployment would add database backups and monitoring.
